# 部署踩坑记录（Docker + PM2 单容器多进程）

> 记录本项目 Docker 部署过程中遇到的实际问题与解法，供后续部署/排查复用。
> 关联文件：`Dockerfile` / `ecosystem.config.cjs` / `nginx.conf` / `.dockerignore`。

---

## 1. 镜像构建

### 1.1 pnpm 下载超时（`registry.npmjs.org` timeout / error 23）
- 现象：`pnpm install` 拉包中途 `The operation was aborted due to timeout`，或 `GET ... error (23)`。
- 原因：默认走 `registry.npmjs.org`，网络环境（国内）不稳定。
- 解法：
  - `Dockerfile` 默认改用国内镜像 `https://registry.npmmirror.com`（`ARG` 可覆盖）。
  - 加大下载容忍度：`npm_config_fetch_timeout = 600000`、`npm_config_fetch_retries = 6`、`npm_config_network_concurrency = 8`。
  - `prisma generate` 额外设置 `PRISMA_ENGINES_MIRROR=https://npmmirror.com/mirrors/prisma`，避免引擎二进制下载被卡。
  - 仍不行再加代理：`--build-arg HTTP_PROXY=... --build-arg HTTPS_PROXY=...`。

### 1.2 prisma generate 在依赖阶段失败
- 原因：依赖层先 `pnpm install`，此时 `prisma/schema.prisma` 尚未拷贝，`postinstall` 里的 `prisma generate` 会失败。
- 解法：依赖层用 `--ignore-scripts` 安装；在构建层拷贝源码后再显式 `pnpm exec prisma generate`。

### 1.3 `UndefinedVar: '$PNPM_HOME'`
- 原因：同一条 `ENV` 里 `PATH="$PNPM_HOME:$PATH"` 自引用，此时 `$PNPM_HOME` 还未定义（Docker 一次性展开为 undefined）。
- 解法：`PNPM_HOME` 单独一条 `ENV`，第二条再引用。

### 1.4 tsbuildinfo 陈旧类型导致构建报错
- 现象：报 `Property 'reason' does not exist on type 'BotTokenResult'`（实际源码类型正常）。
- 原因：`tsconfig.json` 开了 `incremental`，磁盘残留老 `tsconfig.tsbuildinfo` 缓存了旧源码的类型信息。
- 解法：删除 `tsconfig.tsbuildinfo`（并加入 `.gitignore` / 提交时 `git rm --cached`），它属于构建产物，不入库。

## 2. PM2 进程编排（`.cjs` 必须，不能用 `.js`）

### 2.1 `module is not defined in ES module scope`
- 原因：`package.json` 声明了 `"type": "module"`，PM2 加载 `ecosystem.config.js` 时按 ESM，`module.exports` 报错。
- 解法：配置文件改名 `ecosystem.config.cjs`（CommonJS），Dockerfile 的 `CMD` 同步指向 `.cjs`。

### 2.2 指向 `.bin/*` 报 `SyntaxError: Invalid or unexpected token`
- 现象：`script: './node_modules/.bin/next'` / `tsx` 启动即语法错误。
- 原因：pnpm 生成的 `.bin/*` 是 **shell shim**，PM2 却用 Node 以 CJS 方式加载它，把 shell 内容当 JS。
- 解法：不要指向 `.bin/*`，改用：
  - `next`:   `script: './node_modules/next/dist/bin/next'`
  - `tsx`：   `script: './node_modules/tsx/dist/cli.mjs'`
  - 更稳做法：`script:'pnpm' + args:'run <npm script>' + interpreter:'none'`，走 shell 执行 npm 脚本，既避免 shim 也避免 cwd 歧义。

### 2.3 容器直接运行失败：`ENOENT: ... ecosystem.config.js`
- 原因：`.dockerignore` 曾把 `ecosystem.config.js` 排除出镜像，但 `CMD` 又要引用它。
- 解法：不要把运行时配置/启动入口排除，同步 `.dockerignore` 与镜像内文件。

### 2.4 Next 不能套 PM2 cluster
- 现象：多实例 cluster 启动报端口/状态异常，或反复 fork。
- 原因：Next 自己监听 HTTP，PM2 cluster 让多实例共享同一端口会冲突。
- 解法：多 Web 实例改为 **每实例独立端口 + nginx 负载均衡**（见第 3 节）；单实例直接用 `exec_mode:'fork'`。

## 3. nginx 负载均衡（内网穿透场景）

### 3.1 架构
```
公网 xg-2.frp.one:43323 ──frp──▶ 容器:3000(nginx)
                                     │ upstream review_web 轮询
                                     ├─ 127.0.0.1:3001  review-web-3001
                                     ├─ 127.0.0.1:3002  review-web-3002
                                     └─ 127.0.0.1:3003  review-web-3003
  另：review-worker（RabbitMQ 消费者，单实例）
```
- frp 隧道**不用改**：公网端口继续指向容器 `3000` 即可。
- nginx 不是单独部署，而是**容器内的一个进程**，由 PM2 一起托管。

### 3.2 `nginx: [emerg] open() "/dev/stderr" failed (6: No such device or address)`
- 原因：容器内经 PM2 托管、无 tty，`/dev/stderr` 不可用，nginx 报 emerg 退出。
- 解法：`error_log` 改为普通文件路径（如 `/tmp/nginx-error.log`），不要用 `/dev/stderr`。

### 3.3 多实例实例数调整
- 改 `ecosystem.config.cjs` 的 `[3001,3002,3003]` 数组，并**同步** `nginx.conf` 的 `upstream`，端口必须对上。

### 3.4 SSE/长连接转发头（必须）
- 通知走 SSE，nginx 需：`proxy_http_version 1.1`、`proxy_buffering off`、`proxy_set_header Connection ""`、`proxy_read_timeout 1h`。
- 透传域名：`X-Forwarded-Host $host`、`X-Forwarded-Proto $scheme`，供后端生成可访问的 webhook 回调地址。

## 4. 登录/认证（内网 http 访问）

### 4.1 内网穿透 http 下登录不上（cookie Secure）
- 现象：生产环境 `NODE_ENV=production`，cookie 强制 `Secure`；通过 **http://**（非 https）访问时浏览器不保存 `Secure` cookie，登录失效。
- 解法：cookie 的 `secure` 改为**按请求协议动态判定**（`X-Forwarded-Proto: https` 或请求本身 https 才加 Secure），而非写死 production。见 `src/lib/auth/config.ts` 的 `requestUsesHttps()`，`handlers.ts`/refresh/logout 均已接入。

### 4.2 OAuth 回调域名
- 回调/跳转尽量用**相对 `Location`**，由浏览器基于当前域名解析，避免内网穿透改写 Host 后跳到 `localhost`。

## 5. 容器内 `localhost`/`127.0.0.1` 连不到宿主服务（Redis / MySQL / RabbitMQ）

- 现象：
  - worker 反复退出，日志 `[queue] RabbitMQ 不可用，worker 退出`；
  - 登录 OK，但登录后**所有 API 都 500**，后端日志报 `connect ECONNREFUSED 127.0.0.1:3306`（不是负载均衡问题，是 DB 连不上）。
- 原因：`.env` 里的 host 若是 `localhost` **或 `127.0.0.1`**，容器内都指向**容器自身**，而 Redis/MySQL/RabbitMQ 在**另一个容器/宿主**上。
- 前提：这些服务容器已把端口映射到宿主（`-p 6379:6379`、`-p 3306:3306`、`-p 5672:5672`）。

> ⚠️ 关键坑：`--add-host=localhost:host-gateway` **只能改写主机名 `localhost`，对 IP `127.0.0.1` 无效**。URL 里写 `127.0.0.1` 的地址，add-host 救不了，必须换 host 或用网络服务名。

- 解法（按推荐顺序）：
  1. **容器网络互通（首选）**：三个基础服务 + 应用进同一个自定义网络，应用容器里直接用**服务名**访问，彻底免去 host/IP 解析：
     ```bash
     # 先查出三个基础服务的真实容器名（服务名 = 容器名）
     docker ps --format "table {{.Names}}\t{{.Image}}" | grep -Ei "redis|mysql|rabbit"

     NET=review_net
     docker network create $NET
     docker network connect $NET master-redis      # 用你实际容器名
     docker network connect $NET mysql-local
     docker network connect $NET rabbitmq-server

     # 👉 关键：网络建好 ≠ 自动改 URL。必须把 .env 里的 host 一并改成"服务名(容器名)"，
     #    否则 URL 里的 127.0.0.1/localhost 仍指向容器自身，还是连不上（登录后全 500）。
     #    （服务名 = 上面的容器名）
     #   PR_MYSQL_URL  @127.0.0.1:3306 -> @mysql-local:3306
     #   REDIS_URL     @127.0.0.1:6379 -> @master-redis:6379
     #   RABBITMQ_URL  @localhost:5672 -> @rabbitmq-server:5672

     docker rm -f pr-review
     docker run -d --name pr-review --network $NET --env-file .env -p 3000:3000 ai-pr-review
     ```
     基础服务原有的宿主端口映射保留，两者不冲突。
  2. **同一自定义网络 + docker-compose**：把 Redis/MySQL/RabbitMQ 与应用放进一份 `docker-compose.yml`，`depends_on` 保证启动顺序，网络内直接用服务名互访，最省心。
  3. **改 host 为 `host.docker.internal`** + `--add-host=host.docker.internal:host-gateway`（`-e` 覆盖或改 `.env`）。
  4. **仅当 host 是 `localhost`（不是 IP）**才可用 `--add-host=localhost:host-gateway` 一条兜底：容器内 `localhost` 解析到宿主网关。

- 排查命令（查看容器内三个连接实际的 host）：`docker exec pr-review node -e "for(const k of ['PR_MYSQL_URL','REDIS_URL','RABBITMQ_URL']){try{console.log(k,new URL(process.env[k]).hostname)}catch(e){}}"`

## 6. 容器 DNS 解析失败导致 OAuth 登录失败（`EAI_AGAIN`）

### 6.1 现象
- GitHub / Gitee **登录失败**，前端跳回 `/login?error=oauth_failed&provider=xxx`。
- 后端日志（`pm2 logs review-web-*`）报：
  ```
  [auth] OAuth callback failed (gitee): TypeError: fetch failed
    [cause]: Error: getaddrinfo EAI_AGAIN gitee.com
  [auth] OAuth callback failed (github): TypeError: fetch failed
    [cause]: Error: getaddrinfo EAI_AGAIN github.com
  ```
- 注意：授权跳转（`/api/auth/github` 返回 `location: https://github.com/...`）**正常**，失败发生在回调换 token 那一步——应用要 `fetch github.com/gitee.com`，域名解析不出来。

### 6.2 原因
- 容器默认 DNS 是 Docker 内嵌 resolver（`127.0.0.11`）：解析**容器名/服务名**没问题，但**外部域名**（github.com/gitee.com）由它转发给宿主机 DNS（Docker Desktop 上通常是 `192.168.65.x`）。
- 这个转发链路**不稳定**（宿主机默认 DNS 对 gitee.com 甚至全部超时），导致容器内 Node.js 解析外网域名时**间歇性** `EAI_AGAIN`（临时解析失败）。
- 宿主机本身访问 github.com/gitee.com 是通的（返回 200），纯粹是 Docker 转发 DNS 查询这一段出问题。

### 6.3 解法：给容器显式指定公共 DNS
```bash
docker run -d --name pr-review --network review_net --env-file .env \
  --dns 223.5.5.5 --dns 119.29.29.29 \
  -p 3000:3000 ai-pr-review
```
- `223.5.5.5`（阿里 DNS）、`119.29.29.29`（腾讯 DNS）。
- 容器仍走 `127.0.0.11` 解析容器名（服务名互访不受影响），外部域名则直接查询公共 DNS，绕开不稳定的转发。
- 改 docker-compose 时对应 `dns: [223.5.5.5, 119.29.29.29]`。
- 验证容器内解析与连通：
  ```bash
  docker exec pr-review node -e "for(const h of ['github.com','gitee.com','api.github.com']){fetch('https://'+h).then(r=>console.log(h,r.status)).catch(e=>console.log(h,'FAIL',e.cause?.code||e.message))}"
  ```

## 7. 总览：一条可直接用的启动命令

> 前提：三个基础服务容器（示例名为 `master-redis`/`mysql-local`/`rabbitmq-server`，**以 `docker ps` 查出的实际名为准**）已起，且宿主端口映射保留。
> 用**同一网络 + 服务名**互访（见第 5 节），比 `--add-host` 更稳，尤其 `.env` 里 host 是 `127.0.0.1` 时只能走这种。

```bash
# 0) 一次性：按实际服务名(容器名)替换 .env 里三个连接 host（只替换 host，账号/密码/端口不变；先备份）
Copy-Item .env .env.bak
(Get-Content .env) -replace '@127\.0\.0\.1:3306','@mysql-local:3306' -replace '@127\.0\.0\.1:6379','@master-redis:6379' -replace '@localhost:5672','@rabbitmq-server:5672' | Set-Content .env -Encoding utf8

# 1) 建网络并让三个基础服务接入（只在首次需要 network create；用实际容器名）
NET=review_net
docker network create $NET
docker network connect $NET master-redis
docker network connect $NET mysql-local
docker network connect $NET rabbitmq-server

# 2) 构建 & 启动应用容器（同一网络），用户 token 等全从 .env 注入
#    --dns 显式指定公共 DNS，避免 Docker 内嵌 resolver 转发外网域名不稳定导致 OAuth 登录失败（见第 6 节）
docker build -t ai-pr-review .
docker rm -f pr-review
docker run -d --name pr-review --network $NET --env-file .env \
  --dns 223.5.5.5 --dns 119.29.29.29 \
  -p 3000:3000 ai-pr-review
```

验证：
```bash
docker ps | grep pr-review
docker exec -it pr-review node -e "for(const k of ['PR_MYSQL_URL','REDIS_URL','RABBITMQ_URL'])try{console.log(k,'=>',new URL(process.env[k]).hostname)}catch(e){}"
docker exec -it pr-review pm2 ls                  # nginx + web×3 + worker 均 online
docker exec -it pr-review pm2 logs review-worker --lines 20   # 「审查 worker 已启动」
docker exec -it pr-review cat /tmp/nginx-error.log            # nginx 报错用（应为空）
```
