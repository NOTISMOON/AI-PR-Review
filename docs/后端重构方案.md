# AI PR Review 平台后端需求规划提示词

## 一、项目背景

当前正在开发一个 AI Code Review / AI PR Review 平台。

目前前端已经存在部分页面和基础功能，需要根据**当前页面、现有交互和业务功能**，进一步规划后端服务。

本次规划重点不是重新设计前端，也不是单纯罗列 API，而是希望根据现有页面和核心业务流程，系统性规划后端架构、业务模块、数据流以及基础设施。

**技术选型：前后端统一使用 Next.js。**

> 后端不再单独引入 Python / FastAPI。前后端位于同一个 Next.js 项目（App Router）内，采用**模块化单体（Modular Monolith）**：`Route Handlers` 负责对外 HTTP 契约，Server Actions / `Route Handlers` + 服务层承载业务逻辑，后台任务由独立 Worker（同一仓库内的 worker 进程/队列消费者）消费。

后端主要技术方向：

* Next.js（App Router）+ TypeScript —— 前后端统一框架与类型定义
* MySQL + Prisma —— 核心业务数据持久化 ORM
* Redis —— 缓存、状态、未读通知、幂等、分布式临时数据
* BullMQ（基于 Redis 的队列）—— 异步任务与业务事件解耦
* GitHub API —— 仓库、PR、代码、Review、Comment 等数据交互
* GitHub App —— 平台级授权（Installation Token）
* GitHub Webhook —— 监听 GitHub 事件
* LangChain.js / LangGraph.js —— AI PR Review 流程编排
* SSE / WebSocket —— 平台实时通知
* 邮件通知暂时不是核心依赖，可以作为后续扩展能力

其中：

* MySQL 负责核心业务数据和持久化数据
* Redis 负责缓存、状态、未读通知、幂等、分布式场景下的临时数据等
* BullMQ 负责异步任务和业务事件解耦（队列/重试/死信都落在 Redis 上）
* GitHub API 负责仓库、PR、代码、Review、Comment 等数据交互
* GitHub Webhook 负责监听 GitHub 事件
* LangChain.js / LangGraph.js 负责 AI PR Review 流程编排
* SSE / WebSocket 可以用于平台实时通知
* 邮件通知暂时不是核心依赖，可以作为后续扩展能力

# 二、核心业务目标

平台的核心目标是：

> **用户将 GitHub Repository 接入平台后，当 Repository 中出现新的 Pull Request 或 PR 发生代码更新时，平台自动检测 GitHub Webhook 事件，获取 PR 和相关代码信息，通过 AI 进行代码 Review，并将 AI Review 结果回写到 GitHub PR 中。**

同时平台内部还需要支持：

> **后台创建 Review Task / PR Review 任务，并通知指定平台用户，让用户进入 AI PR Review 平台处理对应的评审任务。**

最终形成完整闭环：

```text
GitHub Repository
        ↓
GitHub PR
        ↓
Webhook
        ↓
后端事件接收（Next.js Route Handler）
        ↓
BullMQ
        ↓
AI Review Worker
        ↓
LangGraph.js
        ↓
分析 PR / Diff / Code
        ↓
生成 Review
        ↓
GitHub API
        ↓
回写 PR Review / Comment
```

同时：

```text
后台创建 Review Task
        ↓
MySQL 保存任务
        ↓
BullMQ
        ↓
Notification Service
        ↓
SSE / WebSocket / 平台通知
        ↓
用户进入 Review 平台
        ↓
处理 Review Task
```

# 五、AI Review 使用 LangGraph

AI Review 不希望设计成一个简单的：

```text
Prompt → LLM → Result
```

而是希望后续可以扩展为 LangGraph Workflow（使用 LangChain.js / LangGraph.js 的 Node/TypeScript 版本）。

例如：

```text
Review Start
     ↓
PR Context Node
     ↓
Diff Analysis
     ↓
Code Context Retrieval
     ↓
Bug Analysis
     ↓
Security Analysis
     ↓
Performance Analysis
     ↓
Code Quality Analysis
     ↓
Review Aggregation
     ↓
Review Validation
     ↓
GitHub Review
```

需要考虑：

* LangGraph State
* Checkpoint
* Review Task 状态
* 失败恢复
* 节点重试
* AI 调用失败
* GitHub API 调用失败
* 队列消费失败
* Review 重复执行
* PR 在 AI Review 过程中再次发生 Commit
* Review 版本控制

需要规划 AI Review Job 的生命周期，例如：

```text
PENDING
→ RUNNING
→ ANALYZING
→ REVIEWING
→ COMPLETED
```

异常：

```text
FAILED
CANCELLED
```

# 八、Redis 使用规划

不要为了使用 Redis 而使用 Redis。

需要明确 Redis 在系统中的实际职责。

重点考虑：

## 8.1 Repository / PR 缓存

例如：

```text
github:repo:{repo_id}
github:pr:{repo_id}:{pr_number}
github:pr:files:{repo_id}:{pr_number}
```

需要考虑：

* Cache Aside
* TTL
* PR 更新后的缓存删除
* Webhook 触发缓存失效

## 8.2 Review Task 状态

可以用于：

* AI Job 临时状态
* 分布式任务状态
* LangGraph Checkpoint
* 短期任务上下文

## 8.3 幂等

例如：

```text
github:webhook:{delivery_id}
```

防止 GitHub Webhook 重复处理。

AI Review 也需要考虑幂等 Key：

```text
review:{repo_id}:{pr_number}:{commit_sha}
```

避免同一个 Commit 被重复 Review。

## 8.4 Notification

例如：

```text
notification:user:{user_id}
```

用于：

* 未读数量
* 最新通知
* 在线通知
* 临时消息状态

需要结合 MySQL 判断哪些数据应该持久化，哪些数据只放 Redis。

```text

Worker
```

* 消费幂等
* 持久化（Redis 持久化策略）
* Worker 并发

# 十一、Outbox Pattern

由于系统同时涉及：

```text
MySQL(Prisma)
+
BullMQ(Redis)
+
GitHub API
```

需要重点考虑业务一致性。

例如：

```text
创建 Review Task
      ↓
MySQL Transaction(Prisma)
      ↓
Review Task
+
Outbox Event
      ↓
Commit
      ↓
Outbox Relay
      ↓
BullMQ
      ↓
Notification Worker
```

需要规划：

* Outbox
* Event Status
* Retry Count
* Published At
* Failed At
* Retry Strategy
* Cleanup

避免：

```text
数据库成功
+
队列发布失败
```

导致业务事件丢失。

# 十二、GitHub API 与本地数据的边界

需要明确哪些数据应该：

```text
实时从 GitHub 获取
```

哪些数据：

```text
同步到 MySQL
```

哪些数据：

```text
缓存到 Redis
```

例如：

```text
Repository 基础信息
    ↓
MySQL + Redis

PR 基础信息
    ↓
MySQL + Redis

PR Diff
    ↓
按需 GitHub API 获取 / 短期缓存

AI Review Result
    ↓
MySQL 持久化

Webhook Event
    ↓
MySQL 持久化

Notification
    ↓
MySQL 持久化 + Redis 未读缓存
```

需要根据实际业务量进行判断，而不是所有 GitHub 数据都进行全量同步。

# 十三、系统服务模块规划

前后端统一使用 Next.js，后端不做微服务拆分。

优先按照模块化单体 / Modular Monolith 设计，业务模块在同一个 Next.js 仓库内分层组织：

```text
（对外）
app/api/**        —— Route Handlers（HTTP 契约：webhook / auth / repository / pr / review ...）
app/actions/**    —— Server Actions（后台/交互类变更）

（业务）
src/modules/
├── auth/            —— 用户认证、会话
├── github/          —— GitHub API / GitHub App
├── repository/      —— 仓库同步与浏览数据
├── pull_request/    —— PR 数据
├── review/          —— Review Task
├── ai_review/       —— AI Review Workflow（LangGraph.js）
├── notification/    —— 平台通知
├── webhook/         —— GitHub Webhook
├── queue/           —— BullMQ 基础能力（Producer / Worker / Retry）
├── cache/           —— Redis 封装
├── outbox/          —— 可靠事件投递
└── common/          —— 通用工具 / 类型 / 错误处理

（持久化）
prisma/              —— Prisma Schema / Migration
```

其中：

```text
github/
```

负责 GitHub API / GitHub App。

```text
webhook/
```

负责 GitHub Webhook。

```text
review/
```

负责 Review Task。

```text
ai_review/
```

负责 AI Review Workflow。

```text
notification/
```

负责平台通知。

```text
queue/
```

负责 BullMQ（Redis）基础能力。

```text
cache/
```

负责 Redis。

```text
outbox/
```

负责可靠事件投递。

后台 Worker（AI Review Worker / Notification Worker）在同一个仓库内作为独立进程 / 队列消费者运行，复用同一套 `src/modules` 与 Prisma。
